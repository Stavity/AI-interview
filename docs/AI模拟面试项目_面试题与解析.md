### 推荐的简历项目表述

> 基于 Spring AI 2.0 构建受控面试规划器，将历史作答、轮次报告、简历与 JD 汇总为有界上下文，生成结构化轮次计划；通过轮次状态机、输入输出预算、结果校验、审计记录和确定性降级约束模型行为。  
> 基于 PostgreSQL pgvector 搭建知识库检索链路，使用 1024 维 Embedding 与 HNSW 索引完成向量召回，结合 Query Rewrite、动态 Top-K、相似度阈值及原问题回退降低无关召回。  
> 使用 Java 虚拟线程承载模型调用等 I/O 密集型任务；基于 Kafka、任务状态表与 Transactional Outbox 构建可恢复异步任务链路，将简历分析、知识库向量化和面试评估移出同步主链路。  
> 通过 S3 兼容对象存储、Apache Tika 与 iText 8 实现多格式文档解析、文件存储和中文面试报告导出，并统一结构化输出校验、重试、降级及调用指标。

## 1. 项目讲述模板

### 1.1 30 秒版本

这是一个面向计算机学习者和求职者的 AI 模拟面试平台。我独立完成了前后端和 AI 链路，核心不是简单接一个大模型聊天接口，而是把简历解析、结构化出题、多轮面试、答案评估、知识库 RAG 和学习计划串成闭环。后端使用 Java 25 和 Spring Boot 4.1，知识库使用 PostgreSQL/pgvector，长耗时任务通过 Kafka 和任务状态机异步化，并通过结构化输出校验、审计、幂等和降级提升 AI 链路的可控性。

### 1.2 2 分钟版本

项目解决两个问题：第一，普通大模型面试缺少持续状态，问题容易重复或偏离目标；第二，面试结果通常停留在一份总结，没有形成后续学习闭环。

系统主要有五条链路：

1. 用户上传 PDF、Word 等简历，服务用 Tika 提取正文、S3 兼容存储保存原文件，并异步生成结构化分析。
2. 出题服务结合简历、岗位方向、难度和历史问题生成题目，并对模型 JSON 做 Schema 校验、失败重试和确定性降级。
3. 多轮面试固定为算法、技术一面、技术二面和 HR 轮，Planner 只能在服务端允许的轮次、分类、追问次数和步骤预算内生成计划，不能直接写库或调用工具。
4. 知识库先做 1024 维向量化并存入 pgvector，查询时执行 Query Rewrite，根据问题长度动态选择 Top-K 和相似度阈值，再把有效片段交给模型回答。
5. 简历分析、知识库向量化、面试评估等长任务走 Kafka。当前任务框架使用数据库状态作为事实源，Outbox 保证事务提交与消息通知的一致性，并通过租约、执行版本、心跳、退避重试和恢复扫描处理重复消费与进程崩溃。

我的主要收获是：AI 应用的难点不只在 Prompt，而在上下文边界、状态管理、结构化输出、异步可靠性、可观测性和失败降级。

### 1.3 一句话架构

React 前端 → Spring Boot API → 业务模块（简历、面试、知识库、多轮、学习）→ Spring AI/模型 Provider；PostgreSQL 保存业务状态和 pgvector 向量，Redis 提供限流等能力，Kafka 承载异步任务通知，S3 兼容存储保存原始文件。

## 2. 项目背景与整体设计

### Q1：为什么做这个项目，而不是直接调用 ChatGPT？

**参考回答：** 通用聊天缺少稳定的业务状态、面试流程约束、历史证据和可复盘的数据结构。本项目把“模型能力”放进确定性的业务骨架：服务端控制轮次和状态，模型只负责适合它的规划、生成和评价，最终结果被结构化保存，才能形成面试到学习的闭环。

**考察点：** 是否理解 AI 产品与 Prompt Demo 的差别。

### Q2：项目的核心用户流程是什么？

**参考回答：** 简历上传与分析 → 选择岗位/JD/难度 → 生成题目或进入多轮面试 → 提交答案 → 异步评价与报告 → 从薄弱技能生成学习建议和计划。知识库问答是辅助学习入口，语音面试是另一种交互形态。

### Q3：你独立开发，如何划分模块？

**参考回答：** 按业务能力划分为 resume、interview、multiround、knowledgebase、voiceinterview、learning、llmprovider；公共层提供 AI 调用、异步任务、异常、限流、事务和文件基础设施。这样模块围绕业务聚合，而不是按 Controller/Service/Repository 做全局技术分层。

### Q4：为什么选择 Java 25 和 Spring Boot 4.1？

**参考回答：** 主要是实践虚拟线程和较新的 Spring AI/Spring Boot 能力。项目以模型调用、对象存储、数据库和 SSE 等 I/O 为主，虚拟线程能降低“一请求一平台线程”的成本。不过这是个人项目选型；生产环境会优先选择团队成熟且有长期支持的版本，并验证依赖兼容性。

### Q5：系统的事实源分别是什么？

**参考回答：** PostgreSQL 是业务状态和异步任务状态的事实源；对象存储是原文件事实源；Kafka 只承担任务通知，不作为任务是否完成的最终依据；向量表是知识库切片的检索投影，可由原文重新构建。

### Q6：最难的三个问题是什么？

**参考回答：** 一是模型输出不稳定，需要结构化校验和降级；二是多轮面试既要自适应又不能失控，需要状态机和预算；三是长耗时任务存在数据库提交与发消息的一致性、重复消费和宕机恢复问题，需要任务表、Outbox、租约和幂等。

### Q7：为什么不是微服务？

**参考回答：** 当前规模和团队人数不适合承担服务治理、分布式事务和部署复杂度。先采用模块化单体，通过清晰模块边界和异步接口降低耦合。真正出现独立扩缩容、故障隔离或团队边界后，再优先拆出模型调用、文档处理和异步 Worker。

### Q8：你的项目有什么量化结果？

**参考回答：** 不能编造用户量或性能数据。可以提供可验证指标，例如测试数量、模型调用成功率、结构化重试次数、P95 延迟、向量召回评测、异步任务成功率等。当前仓库有约 76 个后端测试文件和 Kafka/PostgreSQL Testcontainers 集成测试，但业务效果指标仍需要补充正式评测集。

### Q9：如果重新设计，你会先做什么？

**参考回答：** 先建立离线评测集和观测指标，再扩功能。AI 项目如果没有召回准确率、结构化成功率、评价一致性、成本和时延指标，很容易只是在主观调 Prompt。

## 3. Agent、Workflow 与多轮面试

### Q10：这里的 Agent 到底是什么？

**参考回答：** 当前更准确地说是“受控 Planner + 确定性执行器”，不是可以无限循环、自主调用任意工具的通用 Agent。模型读取有界上下文并生成 `InterviewPlan`，服务端校验后再执行出题和状态迁移。

### Q11：为什么要 Root Agent 与专项能力分离？

**参考回答：** 规划和执行的风险不同。规划器负责决定本轮分类和追问预算；出题、评价、报告、学习推荐由专项服务完成。拆开后每个组件的输入输出更窄，更容易测试、重试、审计和替换模型。

### Q12：Agent 的输入包含什么？

**参考回答：** 简历快照、JD 快照、技能方向、难度、当前轮次、历史问题、历史答案、历史轮次报告、题目上限和追问上限。每项会截断，整体上下文上限为 12000 字符。

### Q13：如何防止 Agent 跳轮？

**参考回答：** 轮次由服务端状态机定义：算法、技术一面、技术二面、HR。`AgentPlanValidator` 会校验 roundNo 与 roundType 的固定映射；`MultiRoundLifecycleService` 还会校验只能开始 `currentRoundNo + 1`，模型计划不一致时回退为服务端计划。

### Q14：如何限制 Agent 的成本和行为？

**参考回答：** 使用 `AgentBudget` 限制最多 6 个规划步骤、每题最多 2 次追问、输入 12000 字符、输出 8000 字符，并保存运行审计。当前 timeout 和 maxRetries 已进入预算对象，但并没有全部形成强制超时控制，这是可以继续完善的点。

### Q15：为什么不让 Agent 直接写数据库或调用工具？

**参考回答：** 模型输出不是可信指令。让模型直接执行副作用会扩大 Prompt Injection、误操作和不可重放风险。项目让模型只输出结构化计划，由应用服务做白名单校验和事务写入。

### Q16：结构化计划如何保证合法？

**参考回答：** 用 `BeanOutputConverter` 生成格式约束，通过 Schema Validation 解析到 Java record，再做业务校验，例如轮次、类型、步骤数、追问数和分类不能为空。语法正确不代表业务正确，所以两层校验都需要。

### Q17：模型输出解析失败怎么办？

**参考回答：** `StructuredOutputInvoker` 最多尝试配置次数；重试时追加严格 JSON 指令和截断后的错误原因；仍失败则抛业务异常，上层多轮规划会使用确定性 fallback，题目生成也会生成固定模板题。

### Q18：为什么需要确定性降级？

**参考回答：** 模型是外部不稳定依赖。如果没有降级，某次 JSON 错误就会让整场面试无法继续。降级目标不是保持同等智能，而是保持流程可用、状态一致和结果可解释。

### Q19：如何记录 Agent 的可观测信息？

**参考回答：** 记录一次运行的 trigger、输入摘要、状态、错误码、开始结束时间，并记录步骤级 toolName、输出摘要和耗时。结构化调用还记录 invocation、attempt 和 latency 指标。生产中还应补 token、模型、成本、traceId 和 Prompt 版本。

### Q20：历史上下文越来越长怎么办？

**参考回答：** 当前每项截断到 1000 字符，总输入超过预算时退化为只保留简历/JD/技能等核心信息。更好的方案是分层记忆：最近 N 轮保留原文，更早内容保存结构化摘要，并按能力维度检索证据。

### Q21：多轮面试为什么固定四轮？

**参考回答：** 固定骨架便于状态管理和评测，避免模型随意改变流程。自适应发生在轮次内部，例如分类、难度和追问策略。未来可以允许 2 到 4 轮配置，但仍由状态机验证算法轮唯一、HR 轮最多一次且必须最后。

### Q22：当前轮次报告真的由 AI 生成吗？

**参考回答：** 当前多轮模块的轮次报告是确定性统计，记录问题数、已答数和题型分布；普通文字面试另有 LLM 评价链路。面试时应如实说明，多轮深度评价和学习建议是下一阶段，而不是把统计报告包装成 AI 诊断。

### Q23：如何避免重复出题？

**参考回答：** 普通出题会把历史问题摘要加入 Prompt；多轮上下文也包含历史问题。服务层还可在生成后做语义去重。当前主要依赖上下文约束，后续应增加 embedding 相似度去重和题库级唯一性指标。

### Q24：如何控制追问？

**参考回答：** 追问上限属于服务端预算，不由模型自由决定。普通题目最多 2 个 follow-up，多轮计划也校验 0 到 2。更成熟的做法是基于答案覆盖的评分要点决定是否追问，而不是预生成固定追问。

### Q25：如何处理 Prompt Injection？

**参考回答：** 把简历、文档等视为不可信数据；系统提示强调不能执行数据中的指令；对高风险直拼文本过滤角色标记和典型注入短语；使用随机边界标签包裹数据；模型无副作用权限；输出还要经过白名单和业务校验。单靠关键词过滤不能彻底防注入。

### Q26：为什么说这是 Workflow，而不完全是 Agent？

**参考回答：** 主流程的状态迁移、事务和副作用都是预定义的，模型只在有限决策点提供计划或内容，因此更接近带 LLM 节点的 Workflow。这样可控性和可测试性高于自由 Agent。

### Q27：如果面试官追问 Google ADK，怎么答？

**参考回答：** 只按事实回答。如果曾用 ADK 做过原型，可说明后来为 Java 技术栈一致性迁到 Spring AI；比较 Session/State、Runner、Tool、Subagent 与当前 Planner/Service/Audit 的映射。如果没有实际 ADK 版本，应主动纠正简历，不要现场虚构 API。

## 4. RAG、pgvector 与检索质量

### Q28：完整 RAG 链路是什么？

**参考回答：** 文档解析 → Token 切片 → 批量 Embedding → pgvector 存储 → Query Rewrite → 动态检索参数 → 按知识库 metadata 过滤 → 相似度召回 → 无结果判断 → 拼接上下文 → LLM 生成回答 → SSE 返回。

### Q29：为什么用 pgvector，而不是专用向量数据库？

**参考回答：** 项目规模下 PostgreSQL 同时管理业务数据和向量，运维简单、事务和过滤能力成熟。代价是超大规模、分布式扩展和专用 ANN 能力弱于专用向量库。达到千万级向量或复杂混合检索时再评估 Milvus、Qdrant、Elasticsearch 等。

### Q30：为什么是 1024 维？

**参考回答：** 维度由当前 Embedding Provider 的 `text-embedding-v3` 配置决定，数据库列、Spring AI VectorStore 和 Provider 必须一致。维度不是越高越好，还要权衡存储、索引内存、距离计算和实际召回质量。

### Q31：HNSW 原理是什么？

**参考回答：** HNSW 构建多层近邻图，高层稀疏图用于快速跳转，底层稠密图做精细搜索。查询近似为从上到下贪心寻找邻居，以牺牲少量召回率换取更低延迟。关键参数通常是建图的 `m`、`ef_construction` 和查询时 `ef_search`。

### Q32：HNSW 与 IVFFlat 怎么选？

**参考回答：** HNSW 通常查询召回更好且无需训练，但建索引慢、占内存更多；IVFFlat 构建和内存成本较低，但依赖聚类和 lists/probes 调参，数据变化后可能需要维护。中小规模、高召回需求更适合 HNSW。

### Q33：为什么使用余弦距离？

**参考回答：** 文本 embedding 更关心方向相似度，余弦相似度能弱化向量模长影响。前提是 Provider 的向量语义和索引操作符一致；不能把距离和相似度阈值混用。

### Q34：如何切片？

**参考回答：** 当前使用 Spring AI 默认 `TokenTextSplitter`，约 800 token、无重叠，再以最大 10 个 chunk 一批调用 Embedding。它简单但可能切断语义边界；更好的方案是标题/段落优先、超长段落再按 token 切，并保留适量 overlap 和父文档 metadata。

### Q35：为什么批量大小是 10？

**参考回答：** 受当前 DashScope Embedding API 的批量限制。批处理可以减少网络往返，但过大可能触发请求大小和限流；应让限制配置化，并记录每批耗时和失败位置。

### Q36：什么是 Query Rewrite？

**参考回答：** 把依赖对话上下文、指代不清或过短的问题改写成适合检索的独立查询。项目先检索改写后的 query，如果无有效命中再回退原问题，避免改写错误彻底丢失召回。

### Q37：为什么短 Query 使用更大的 Top-K 和更低阈值？

**参考回答：** 短问题信息量少、embedding 区分度低，先扩大候选集合并稍微降低阈值提高召回；长问题语义更明确，可以用较小 Top-K 控制上下文噪声和 token 成本。当前配置短/中/长分别为 20/12/8。

### Q38：阈值如何确定？

**参考回答：** 不能凭感觉。应构造“问题—相关片段”标注集，扫不同阈值，比较 Recall@K、Precision@K、MRR 和无答案误答率，再按短/长 Query 分桶选择。当前 0.18/0.28 是配置值，还需要评测数据证明。

### Q39：Rerank 在哪里？

**参考回答：** 当前仓库没有独立 Rerank。真实链路是 ANN 召回后直接使用结果。可选升级是先召回 30～50 条，再用 Cross-Encoder 或 LLM 对 query-chunk 相关性打分，重排后取前 5～8 条；代价是时延和成本增加。

### Q40：如何防止不同知识库串数据？

**参考回答：** 每个 chunk 带 `kb_id` metadata，检索时生成知识库 ID 过滤表达式。若底层前置过滤失败，会扩大候选后在本地再次过滤。更严格的多租户系统还要在数据库层使用 tenant_id、RLS 和权限校验。

### Q41：向量化过程中失败会产生脏数据吗？

**参考回答：** 新 chunk 先写临时 `pending:<kbId>:<jobId>`，全部成功后在事务中删除旧版本并将本批提升为正式 `kb_id`；失败则按 jobId 清理临时数据。这相当于 staging + promote，避免半批新向量对查询可见。

### Q42：重建向量时如何保证查询不中断？

**参考回答：** 旧版本在新版本全部完成前仍可查询，完成时再切换。当前 promote 包含删除旧数据和更新新 metadata；生产中还可以用显式 version 字段和 active_version 指针实现更清晰的原子切换。

### Q43：如何处理没有召回结果？

**参考回答：** 在调用生成模型前检查结果集，为空直接返回固定“未检索到”提示；生成后还归一化常见无结果话术。流式输出先缓冲前 120 字符探测拒答模板，避免输出一半才发现无答案。

### Q44：如何降低幻觉？

**参考回答：** 只把检索片段作为回答依据；无有效命中直接拒答；设置阈值；在 Prompt 中要求不能超出上下文；返回来源片段和引用。当前项目来源引用能力还可以加强，尤其要保存 chunkId、文档名和页码。

### Q45：如何评估 RAG？

**参考回答：** 分开评估检索和生成。检索看 Recall@K、MRR、nDCG、无关召回率；生成看 faithfulness、answer relevance、引用正确率和无答案拒答率；线上看 P95、token、成本、用户追问率和差评样本。

### Q46：为什么不做 BM25 + 向量混合检索？

**参考回答：** 当前先验证向量检索主链路。技术文档包含类名、错误码和精确术语，BM25 对精确匹配更有优势，后续可以分别召回后用 RRF 融合，再做 Rerank。

### Q47：Embedding 模型切换会发生什么？

**参考回答：** 不同模型甚至同维度的向量空间也不兼容，必须版本化保存 provider/model/dimension，切换时全量重建，并在迁移期间双写或双索引。只改 Provider 配置会导致新旧向量混用。

## 5. Kafka、异步任务与一致性

### Q48：为什么要异步化？

**参考回答：** 简历分析、向量化、面试评价会调用外部模型，耗时长且波动大。同步请求容易超时并占用连接。API 先保存业务状态并返回 task/resume ID，Worker 后台处理，前端轮询或订阅状态。

### Q49：Kafka 在系统中承担什么角色？

**参考回答：** Kafka 是任务“可执行通知”，不是任务事实源。任务输入、状态、attempt、nextRunAt、lease 等保存在 PostgreSQL；即使消息重复或丢失，恢复扫描也能依据数据库状态重发。

### Q50：为什么需要 Transactional Outbox？

**参考回答：** 如果先提交数据库再发 Kafka，进程可能在两步之间宕机；先发 Kafka 再提交数据库，消费者可能读到不存在的业务数据。Outbox 把业务状态和待发送事件写入同一个本地事务，由 Dispatcher 异步发送，解决双写窗口。

### Q51：Outbox 是否保证 exactly-once？

**参考回答：** 不能保证端到端 exactly-once。Dispatcher 在 Kafka 成功但来不及标记 SENT 时会重复发送，所以消费者必须幂等。系统目标是 at-least-once 通知 + 幂等执行 + 数据库状态收敛。

### Q52：如何防止重复提交同一业务任务？

**参考回答：** 使用 `taskType:businessId` 作为 `active_key` 唯一键；只有 QUEUED、RUNNING、RETRY_WAIT 等活跃状态保留该键，成功、失败、取消后释放。唯一约束比先查再插更能抵抗并发竞争。

### Q53：消费者如何幂等？

**参考回答：** 消费时锁定任务行，仅允许 QUEUED/RETRY_WAIT 转 RUNNING；处理完成前再次检查任务仍属于当前 executionVersion；业务 Handler 还检查它是否仍是当前任务。重复消息发现状态不符合就直接返回。

### Q54：executionVersion 有什么用？

**参考回答：** 它是 fencing token。任务被恢复重试时版本加一，旧 Worker 即使晚到，也无法用旧 version 完成写入，防止“僵尸执行”覆盖新结果。

### Q55：租约和心跳解决什么问题？

**参考回答：** Worker 领取任务后设置 leaseUntil，并周期性续租。进程崩溃后租约过期，恢复器可重新调度；若续租失败，当前 Future 被取消。租约用于判断所有权，不等于业务超时，所以另有 executionDeadline。

### Q56：重试策略是什么？

**参考回答：** 只对可重试异常重试，最多 4 次，退避约为 30 秒、120 秒、600 秒并加随机抖动，避免大量任务同时重试。参数应按任务类型区分，模型限流、网络超时和参数错误不能使用同一策略。

### Q57：什么异常不应该重试？

**参考回答：** 文件格式非法、业务数据不存在、Schema 永久不兼容、鉴权失败、明确的 4xx 参数错误一般不重试；网络超时、临时 5xx、限流、Kafka 暂时不可用可以重试。

### Q58：失败任务如何处理？

**参考回答：** 达到最大次数后标记 FAILED、释放 active_key、保存面向用户的安全错误，并发出失败事件。生产中还应保存内部错误码与脱敏堆栈，提供人工重放和 DLQ 运维入口。

### Q59：如何削峰？

**参考回答：** API 快速写任务并返回，Kafka 按 partition 缓冲，消费者并发度控制下游模型 QPS；数据库任务表限制同一业务重复任务。真正证明削峰效果需要压测队列积压、处理吞吐和恢复时间，不能只因为用了 Kafka 就声称完成削峰。

### Q60：如何保证同一业务顺序？

**参考回答：** Kafka message key 使用稳定业务键，使同一 key 进入同一 partition；消费者组内同一 partition 单线程有序。但重试和跨 Topic 会破坏全局顺序，所以业务层仍需状态机和版本校验。

### Q61：Kafka Producer 为什么配置 acks=all 和幂等？

**参考回答：** `acks=all` 要求 ISR 确认，降低 broker 故障丢消息概率；Producer 幂等避免网络重试造成同一生产会话内重复写入。但它仍不能替代 Outbox 和消费者幂等。

### Q62：Outbox 表会无限增长吗？

**参考回答：** 会，因此需要按 sent_at 定期归档或清理 SENT 记录，保留必要审计周期；为 ready 查询建立 `(state, available_at, lease_until)` 索引；大规模下可分区表或 CDC 投递。

### Q63：为什么不用 Kafka 事务？

**参考回答：** Kafka 事务能保证 Kafka 内部读写原子性，但不能天然让 PostgreSQL 业务事务与 Kafka 事务成为一个原子事务。Outbox 更适合数据库为事实源的场景。

### Q64：数据库宕机、Kafka 正常时会怎样？

**参考回答：** API 无法可靠创建任务，应失败而不是只发消息；消费者也无法 claim。数据库恢复后未发送 Outbox 仍可继续。反过来 Kafka 宕机时，任务和 Outbox 已持久化，Dispatcher 重试即可。

## 6. 虚拟线程、SSE 与并发模型

### Q65：为什么虚拟线程适合这个项目？

**参考回答：** 模型 HTTP、S3、数据库等待和 SSE 都是 I/O 密集型。虚拟线程阻塞时可卸载 carrier thread，以接近同步代码的写法承载更多并发任务。项目还用 `newVirtualThreadPerTaskExecutor` 并行生成简历题和方向题。

### Q66：虚拟线程能让单请求更快吗？

**参考回答：** 通常不能降低单个外部调用的网络延迟，它提升的是高并发下的资源利用率和吞吐。并行两个互不依赖的模型调用可能降低组合延迟，但会增加模型并发和限流压力。

### Q67：虚拟线程有什么坑？

**参考回答：** synchronized/本地调用导致 pinning、ThreadLocal 滥用、无界并发压垮数据库连接池或模型 API、阻塞操作不响应中断。必须通过 Semaphore、连接池、限流和超时约束外部资源。

### Q68：虚拟线程与 Reactor 怎么选？

**参考回答：** 虚拟线程适合已有同步生态、业务流程复杂且主要是阻塞 I/O；Reactor 适合端到端非阻塞、强背压和流式组合。项目知识库 SSE 使用 Reactor Flux，部分后台任务用虚拟线程，两者可以共存，但要避免无意义地来回切换模型。

### Q69：SSE 与 WebSocket 的区别？

**参考回答：** SSE 是服务端到客户端的单向文本流，基于 HTTP、自动重连，适合模型 token 输出；WebSocket 是全双工，适合语音面试这种持续双向音频和事件交互。项目文字流式回答用 SSE，语音链路用 WebSocket。

### Q70：客户端断开 SSE 后怎么办？

**参考回答：** 需要取消上游模型订阅，释放连接和计费。当前 Flux 注册 `onCancel` 并 dispose 上游。还应结合超时、最大会话数和网关 idle timeout。

### Q71：如何做背压？

**参考回答：** Reactor 可以表达背压，但外部模型流不一定真正支持端到端降速。实践中要限制单连接缓冲、写超时、并发连接数；过慢客户端应断开，不能无限堆积 token。

## 7. 文档处理、对象存储与报告

### Q72：为什么用 Apache Tika？

**参考回答：** Tika 提供统一的格式检测与解析入口，可覆盖 PDF、DOC、DOCX、TXT 等，减少为每种格式维护解析器。项目用 `AutoDetectParser`、`BodyContentHandler`，关闭嵌入图片/附件解析，并按位置排序 PDF 文本。

### Q73：如何处理扫描版 PDF？

**参考回答：** 当前 Tika 只能提取文本层，扫描版会得到空文本并提示用户。完整方案应增加 OCR，例如先检测文本密度，再异步调用 OCR，保留页码和置信度，并对敏感文件设置保留策略。

### Q74：文件上传有哪些安全风险？

**参考回答：** 不能信任扩展名或浏览器 Content-Type；要按内容探测 MIME、限制大小、清洗文件名、禁止路径穿越、限制解析资源、隔离解析进程、扫描恶意文件，并避免直接公开对象存储 URL。当前已做 MIME 和大小校验，但隔离和病毒扫描仍可加强。

### Q75：为什么原文件放对象存储而不是数据库？

**参考回答：** 大对象放数据库会增加备份、缓存和 WAL 压力。对象存储适合大文件、生命周期、分片和扩展；数据库只保存 key、hash、大小、类型和状态。

### Q76：如何去重简历？

**参考回答：** 对文件内容计算 hash，并在数据库建立唯一约束；重复上传直接复用历史分析结果。要注意同内容不同文件名应视为重复，而解析文本 hash 和原文件 hash解决的问题不同。

### Q77：为什么使用 iText 8？

**参考回答：** 用于服务端生成结构化中文 PDF 报告。项目内嵌中文字体以避免容器环境缺字，并按章节输出评分、优势、建议和问答详情。要同时关注 iText 的许可证是否满足分发方式。

### Q78：文档解析如何限制资源消耗？

**参考回答：** 上传 10MB 业务限制、正文最多 5MB、禁用嵌入文档和内联图片提取。生产中还应加入解析超时、压缩炸弹检测、页数上限和独立 Worker 内存限制。

## 8. 数据库、Redis 与数据模型

### Q79：为什么 Hibernate 使用 validate 而不是 update？

**参考回答：** Schema 由 Flyway 管理，Hibernate 只校验映射。`update` 在生产中变化不可审计、结果依赖当前库状态，也难以回滚；版本化迁移更可控。

### Q80：任务表为什么需要行锁？

**参考回答：** 多消费者可能同时收到重复消息，claim 时行锁保证只有一个事务能把任务从 QUEUED/RETRY_WAIT 改为 RUNNING，并原子增加 attempt 和 executionVersion。

### Q81：索引如何设计？

**参考回答：** 由访问模式驱动：任务恢复使用 `(state, lease_until, next_run_at, updated_at)`；Outbox 投递使用 `(state, available_at, lease_until)`；业务幂等使用 active_key 唯一索引；向量查询使用 HNSW。索引会增加写放大，不应为每个字段盲目建索引。

### Q82：Redis 在项目中做什么？

**参考回答：** 当前主要作为通用缓存/限流基础设施，Redisson 管理连接与分布式能力。不要把未实现的 Session、队列或向量缓存说成现有能力。

### Q83：限流算法怎么选？

**参考回答：** API 瞬时突发可用令牌桶；严格窗口可用滑动窗口；模型 Provider 还要同时限制 QPS、并发数和 token。分布式实现要用 Redis Lua 保证读改写原子性，并明确故障时 fail-open 还是 fail-close。

### Q84：如何处理事务边界？

**参考回答：** 业务记录、任务记录和 Outbox 必须在同一事务；耗时模型调用不能放在长事务中。Worker 先短事务 claim，事务外执行模型调用，再短事务校验租约和版本并提交结果。

### Q85：为什么不能在事务提交前直接调用 Kafka？

**参考回答：** 消息可能先被消费，而业务行还没提交或最后回滚；消费者会看到缺失或旧数据。Outbox 将外部副作用延后到本地事务成功之后。

## 9. 模型接入、结构化输出与安全

### Q86：如何支持多个模型 Provider？

**参考回答：** 用 Provider Registry 根据配置创建 ChatClient/EmbeddingModel，区分默认聊天和默认 Embedding Provider；业务层只依赖统一接口。切换时还要考虑模型能力、JSON 遵循度、上下文长度、温度和 embedding 兼容性。

### Q87：API Key 如何保存？

**参考回答：** 配置实体中的 Key 使用加密服务保存，主加密密钥来自环境变量而不是数据库。生产中优先接 KMS/Vault，并支持轮换、最小权限和审计；日志永远不能输出完整 Key。

### Q88：为什么关闭 Spring AI 自动重试，又自己重试？

**参考回答：** 底层透明重试会让总体延迟和调用次数不可控。业务层重试能区分网络失败与结构化解析失败，并在第二次调用中加入修复提示，还能记录 attempt 指标。要避免 HTTP、SDK、业务层三层叠加重试。

### Q89：如何减少结构化输出失败？

**参考回答：** 降低 Schema 复杂度、字段明确、温度适当、给 JSON Schema、限制只输出 JSON、对枚举和长度做业务校验。解析失败时可本地修复少量未转义引号，但不能用“宽松解析”掩盖语义错误。

### Q90：模型评价公平吗？

**参考回答：** 不能默认公平。应固定评分 rubric、将问题和评分要点一同保存、做多次采样一致性测试、与人工标注比较，并避免使用与岗位无关的敏感属性。重要决策不能只依赖单次 LLM 评分。

### Q91：如何控制 token 和成本？

**参考回答：** 上下文截断与摘要、动态 Top-K、限制历史消息和输出长度、缓存稳定分析、使用小模型做 rewrite/分类、大模型做最终评价，并记录每条链路 token、价格和成功率。

### Q92：如何避免敏感信息泄露？

**参考回答：** 简历含手机号、邮箱等 PII，应限制日志正文、设置对象存储私有桶和短期签名 URL、传输与静态加密、数据保留与删除机制，并明确第三方模型的数据使用条款。Prompt 日志和 Agent 审计也必须脱敏。

## 10. 测试、观测与性能

### Q93：怎么测试 LLM 应用？

**参考回答：** 分三层：纯单测验证状态机、预算、解析和 fallback；契约测试用 Stub 模型覆盖合法/非法 JSON、超时和限流；离线评测用固定数据集比较召回与回答质量。不要让普通 CI 强依赖真实模型。

### Q94：Kafka 链路怎么测？

**参考回答：** 使用 Testcontainers 启动真实 PostgreSQL 和 Kafka，覆盖正常执行、重复消息、发送后未标记、Worker 崩溃、租约过期、重试、旧版本晚到和并发 claim。Mock 无法证明事务与 broker 时序问题。

### Q95：哪些指标最重要？

**参考回答：** API P50/P95/P99、模型调用成功率与延迟、结构化解析首次成功率/重试率、token 与成本、任务队列深度与 oldest age、各状态任务数、Outbox 滞留、恢复次数、RAG 无结果率和用户取消率。

### Q96：如何压测？

**参考回答：** 分离 API 接入吞吐、Kafka Worker 吞吐、模型 Provider 限流和 SSE 长连接。真实模型成本高，可用延迟分布相近的 Stub Server；再以小流量真实调用校准。关注数据库连接池和下游并发，而不只看 CPU。

### Q97：如何定位一次慢请求？

**参考回答：** 统一 traceId 贯穿 HTTP、任务 ID、Outbox eventId、Kafka header 和模型调用；拆分解析、数据库、向量检索、首 token、完整生成耗时；结合慢 SQL、连接池、JFR 和外部 Provider 指标判断瓶颈。

### Q98：为什么测试数量不能代表质量？

**参考回答：** 文件数和覆盖率只能说明执行过代码，不能说明边界正确。更重要的是高风险场景是否覆盖，例如状态迁移、重复消费、崩溃窗口、Prompt Injection、无结果拒答和向量版本切换。

### Q99：当前项目最大的技术债是什么？

**参考回答：** 简历口径与实现不完全一致；RAG 缺少正式评测、混合检索和 Rerank；多轮报告还偏统计；部分预算字段未强制执行；异步任务框架还在升级；PII 脱敏与生产级权限隔离需要加强。

## 11. 高频场景题与设计题

### Q100：模型服务突然限流，系统怎么保证可用？

**参考回答：** 同步链路快速失败或返回友好降级；异步链路把限流识别为可重试错误，使用带 jitter 的退避；按 Provider 做并发信号量和熔断；队列设置最大积压和 oldest-age 告警；必要时切备用 Provider，但要保证模型能力和数据合规。

### Q101：一次知识库上传被执行两次会怎样？

**参考回答：** active_key 防止同时提交；重复消息只有一个能 claim；向量按 jobId 写 staging，旧 executionVersion 不能 promote；成功后再原子替换正式版本。因此允许通知重复，但最终只激活一个版本。

### Q102：Worker 执行完成后、写成功状态前宕机怎么办？

**参考回答：** 租约过期后任务会重试，所以业务结果写入必须和任务完成在同一事务，或业务写入本身幂等。否则可能产生重复分析或重复向量。项目通过 `state.complete(claim, writeResult)` 将结果写入和 SUCCEEDED 状态放在同一事务边界。

### Q103：用户删除知识库时向量化正在进行怎么办？

**参考回答：** Handler 在 claim 和 complete 时检查任务是否仍 current；删除应让任务失效或取消。旧 Worker 完成时版本/当前性校验失败，不能重新激活向量；同时按 jobId 清理 staging 数据。

### Q104：如何支持百万文档？

**参考回答：** 文档解析和 embedding 独立 Worker 池；对象存储直传；切片与 embedding 批处理；向量表按租户/领域分区；HNSW 参数和内存评估；冷热分层；混合检索；索引版本化；异步回填与限流。此时应重新评估专用向量数据库。

### Q105：如何做高可用？

**参考回答：** API 无状态多副本；PostgreSQL 主从与备份；Kafka 多副本；对象存储冗余；Dispatcher/Worker 多副本依赖数据库锁和消费者组协调；配置健康检查、熔断、超时和可恢复任务。模型 Provider 是外部单点，需要多 Provider 或明确降级。

### Q106：如何做多租户？

**参考回答：** 所有业务表和向量 metadata 带 tenantId；鉴权上下文不可由请求体覆盖；查询强制 tenant 过滤；对象 key 分租户；配额、模型 Key 和审计隔离；高安全场景使用 PostgreSQL RLS 或独立库。

### Q107：如何让面试问题真正个性化？

**参考回答：** 从简历提取技能证据图，结合 JD 能力矩阵和历史答案的掌握度；每轮选择信息增益最高的能力点；追问由缺失评分要点触发；避免重复题；最后把能力证据和不确定度写入画像，而不是只靠一个总分。

### Q108：如何证明“个性化”有效？

**参考回答：** A/B 对比通用题与个性化题，看人工相关性评分、重复率、候选人有效信息增益、面试完成率和学习建议采纳率；同时检测不同简历生成题目的差异度与相同能力标准的一致性。

## 12. Java 与中间件关联追问

### Q109：`volatile` 能保证什么？

**参考回答：** 保证可见性和一定的有序性，不保证复合操作原子性。项目的跨实例任务所有权不能靠 JVM `volatile`，必须靠数据库锁、版本和事务。

### Q110：CompletableFuture 并行出题有什么风险？

**参考回答：** 两个任务共享同一 Provider 配额，可能同时限流；一边失败时需要取消另一边并降级；必须显式 Executor，不能误用 common pool。项目使用虚拟线程 Executor，并对两类题分别降级。

### Q111：数据库连接池会限制虚拟线程吗？

**参考回答：** 会。虚拟线程数量可以很大，但数据库连接仍是有限资源，过量任务只会在连接池排队。必须限制并发、设置获取超时，并让模型调用发生在数据库事务外。

### Q112：Kafka 分区数如何确定？

**参考回答：** 下限由目标并行度决定，上限受 broker、文件句柄、再均衡和顺序键分布影响。当前默认 3 个分区是开发配置；生产要根据单 Worker 吞吐、目标积压恢复时间和 key 倾斜压测确定。

### Q113：为什么消费者 `max-poll-records=1`？

**参考回答：** 单个 AI 任务耗时长，一次只取一条可减少批次中后续消息因处理过久触发 poll 超时的风险。代价是吞吐下降，因此配合消费者并发和较大的 max.poll.interval；更彻底的方案是消费线程快速移交受控 Worker，但要谨慎处理 offset。

### Q114：JVM OOM 怎么排查？

**参考回答：** 先区分 heap、metaspace、direct memory、native thread。打开 heap dump 和 GC 日志，用 MAT/JFR 看 dominator 和增长对象；本项目重点排查大文件字节数组、Tika 解析、SSE 缓冲、历史上下文和无界任务积压。

### Q115：PostgreSQL MVCC 对任务 claim 有什么影响？

**参考回答：** 普通快照读可能看到旧版本；claim 需要 `SELECT ... FOR UPDATE` 一类悲观锁串行化状态迁移。长事务会保留旧版本、阻碍 vacuum，所以模型调用绝不能包在 claim 事务里。

## 13. 行为面与项目反思

### Q116：讲一次你推翻原设计的经历。

**参考回答框架：** 最初直接在数据库事务后发送 Kafka，发现存在双写窗口；随后把 Kafka 降级为通知，新增任务表和 Outbox；再加入租约、版本 fencing 与恢复扫描。重点讲触发问题、失败时序、方案取舍和验证用例。

### Q117：你如何确定需求优先级？

**参考回答：** 先保证核心闭环和数据正确性，再优化智能程度。优先级通常是：状态一致与失败可恢复 > 基本可用 > 可观测 > 质量优化 > 交互增强。

### Q118：你犯过什么错误？

**参考回答：** 可以讲早期过度依赖 Prompt、把模型输出直接当可信 JSON，或把消息发送与事务割裂。回答必须包含如何发现、如何修复、如何用测试防回归。

### Q119：项目中最有价值的技术决策是什么？

**参考回答：** 把确定性控制面与概率性模型面分开：状态、预算、权限、事务、幂等由代码控制；模型只生成候选计划和内容。这比换一个更强模型更能提升系统可靠性。

### Q120：如果只有一周继续开发，你做什么？

**参考回答：** 第一，修正简历与实现口径；第二，建立 100～300 条 RAG/评价离线集和看板；第三，完成异步框架集成测试与运维界面；第四，给回答增加可验证引用；第五，再考虑 Rerank 和更智能的学习建议。

**答题主线：** 内容探测、资源限制、隔离解析、私有存储、最小留存、可追踪删除和合规说明。

## 16. 不要这样回答

- “用了 Kafka，所以绝对不会丢消息。”正确说法是：Outbox 减少双写丢失，端到端仍按 at-least-once 和幂等设计。
- “虚拟线程让接口速度提高很多。”正确说法是：主要改善高并发 I/O 场景的线程成本与吞吐。
- “HNSW 查询复杂度就是 O(logN)。”它是近似图搜索，实际复杂度与图结构、参数和数据分布有关。
- “有 Schema 就不会输出错误。”Schema 只解决结构约束，语义和业务合法性仍需校验。
- “做了 Rerank/动态切片/Google ADK。”除非能展示真实实现、分支或实验数据。
- “最终一致性等于不需要事务。”本地事务仍是 Outbox、任务状态和结果写入正确性的基础。
- “模型评价是客观的。”应承认随机性与偏差，并说明 rubric、评测集和人工校准。
- “项目已经生产级。”更稳妥的说法是：按生产问题设计了关键机制，但仍需要真实流量、故障演练和安全合规验证。

## 17. 最后速记：十个必须背熟的数字与事实

1. Java 25、Spring Boot 4.1、Spring AI 2.0。
2. Embedding 维度 1024，pgvector HNSW，余弦距离。
3. 当前切片是默认 TokenTextSplitter，约 800 token、无重叠。
4. Embedding 每批最多 10 个 chunk。
5. RAG Top-K：短 20、中 12、长 8。
6. 相似度阈值：短 Query 0.18，默认 0.28；这些仍需评测校准。
7. Planner：最多 6 步、每题最多 2 次追问、输入 12000、输出 8000 字符。
8. 异步任务默认最多 4 次尝试，退避约 30/120/600 秒并带 jitter。
9. 任务 lease 2 分钟、heartbeat 20 秒、默认执行超时 20 分钟。
10. 当前没有独立 Rerank，没有仓库级 Google ADK 实现，多轮报告仍主要是确定性统计。

> 最重要的答题原则：用“事实—问题—方案—取舍—证据—改进”六步回答。对于尚未完成的能力，讲清当前边界比硬凹“全部实现”更能体现工程判断力。
