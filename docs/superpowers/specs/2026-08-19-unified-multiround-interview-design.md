# 多轮面试统一入口与算法轮设计

## 1. 目标

将多轮面试作为系统中的正式面试形式，而非仅存在于简历详情页的附属功能。用户可从模拟面试中心或简历详情启动，在最近面试和面试记录中查看、继续多轮会话。

算法轮固定为三道 LeetCode Medium 风格的算法题。三题在轮次启动时生成并持久化，页面默认展示第一题，用户可通过题号 Tab 切换。每题分别保存代码、语言、提交状态和 AI 静态评审结果。

## 2. 非目标

- 不引入代码运行、隐藏用例或在线判题。
- 不迁移历史数据，不重建现有单轮或语音面试表。
- 不让 Agent 直接修改轮次状态、题目状态或数据库。

## 3. 面试类型和入口

### 3.1 类型模型

`InterviewSessionEntity.sourceType` 是统一会话类型的判别字段：

| sourceType | 形式 | 详情入口 |
| --- | --- | --- |
| 普通值 | 文字模拟面试 | 既有文字会话页 |
| `KNOWLEDGE_BASE` | 知识库面试 | 既有知识库会话页 |
| `MULTI_ROUND` | 多轮面试 | 多轮面试页 |
| 语音独立会话 | 语音模拟面试 | 既有语音会话页 |

多轮面试继续通过 `multi_round_interviews` 一对一扩展 `interview_sessions`。轮次、题目、算法提交和报告仍由 `modules.multiround` 负责。

### 3.2 模拟面试中心

面试形式增加 `multi_round`。选中该类型后：

- 简历为必填项，且必须已完成解析和分析。
- Skill、难度和可选 JD 与简历详情入口采用同一请求模型。
- 点击开始先按 `resumeId + skillId + difficulty + normalizedJd` 查找进行中的同范围会话；存在则进入该会话，否则创建新会话。
- 文字和语音的现有启动行为不变。

### 3.3 简历详情

保留多轮面试快捷入口。恢复请求必须携带当前选择的 Skill、难度和 JD，不得仅以 `resumeId` 恢复任意进行中会话。

### 3.4 最近面试和面试记录

统一查询文字会话、语音会话和 `MULTI_ROUND` 会话；前端映射为同一种展示项。多轮条目显示：类型、当前轮次、总轮次、进行状态和创建时间。点击或继续按钮进入 `/multi-round?sessionId=...`。

删除、导出和单轮报告操作不应用于多轮条目，除非已有对应的多轮专用能力；多轮条目的操作只提供继续/查看报告。

## 4. 算法轮规则

### 4.1 题目约束

算法轮为唯一受本设计影响的轮次：

- `questionLimit` 固定为 3。
- 所有题目的 `questionType` 固定为 `ALGORITHM`。
- 题目难度固定为 `medium`；新增持久化字段或受控元数据承载该难度。
- 每题必须含完整题意、输入输出说明、约束、至少一组示例和参考解题要点。
- 三题覆盖不同核心算法维度，例如数组/双指针、树图、动态规划或二分；Agent 只能从受控分类中提出覆盖计划，后端负责强制校验。
- 模型生成失败时使用内置的三道完整 Medium 级降级题，不能使用泛化占位文本。

技术一面、技术二面和 HR 面保留各自题型策略。它们的题数不再由算法轮的三题要求隐式决定。

### 4.2 状态机

算法题的状态至少区分 `PENDING`、`ANSWERED`、`EVALUATED`：

1. 启动算法轮时，持久化三道 `PENDING` 题。
2. 对某题提交代码后，保存对应语言和代码快照，题目转为 `ANSWERED`。
3. 静态评审成功后题目转为 `EVALUATED`；评审失败时保留代码快照并允许重试。
4. 三题均已提交并完成评审后，算法轮可以结束。

提交接口必须校验题目所属轮次为 `ALGORITHM` 且轮次进行中。每一道题使用独立 idempotency key，不同题之间不能互相复用提交结果。

## 5. 前端交互

算法轮不再逐题堆叠卡片和单个编辑器，而是：

1. 顶部展示三个稳定宽度的题号 Tab，并标注每题状态。
2. 当前 Tab 展示该题完整题面和唯一对应的 `AlgorithmEditor`。
3. 编辑器用 `questionId` 作为状态边界：语言、草稿、提交 key、评审结果均按题目隔离；切换 Tab 后恢复该题本地状态或已保存提交结果。
4. 各题均可独立提交、重试评审和切换语言，不影响其他题。
5. 轮次操作使用外层容器和独立操作按钮，不在 `button` 内嵌套 `button`。

非算法轮仅渲染当前待回答问题的文本输入，提交后自动聚焦下一道待答题；不复用算法编辑器。

## 6. 编排边界

Google ADK 的职责是依据简历、JD、历史表现和允许分类，提出当前轮的结构化 `InterviewPlan`，包括算法三题的覆盖维度。它不拥有领域状态机。

Spring 服务负责：

- 将算法轮约束为三道 Medium `ALGORITHM` 题。
- 校验题目覆盖、轮次顺序、幂等和状态转换。
- 持久化题目、代码和评审结果。
- 在 ADK 不可用时使用完整的受控降级题与确定性计划。

运行模式为 `GOOGLE_ADK` 时使用 ADK Runner；`SHADOW` 和 `LEGACY` 的回退行为必须保留可观测审计。默认运行时是否切换不属于本次产品闭环改造。

## 7. 实现边界

### 后端

- 为多轮会话提供轻量列表 DTO/API，供模拟面试中心和面试记录页合并查询。
- 增加按范围查找活动会话的接口，替代仅按简历恢复的接口。
- 将轮次题数策略提取为显式策略：算法轮固定 3，其他轮次使用各自配置。
- 强化算法出题 prompt、输出 DTO 和持久化校验；增加 Medium 难度与三题互异性元数据。
- 在算法提交/评审服务中推进题目状态，并禁止不合法的跨轮提交。

### 前端

- 扩展 `InterviewMode`、模拟面试中心启动分支、最近面试聚合和面试记录筛选。
- 多轮记录独立展示和路由，避免误调用文字面试删除或导出接口。
- 重写算法轮的题目选择区域和编辑器状态管理。

## 8. 测试与验收

后端：

- 多轮列表仅返回 `MULTI_ROUND` 会话，范围恢复不会返回不同 Skill、难度或 JD 的活动会话。
- 算法轮创建时固定三题、全部 `ALGORITHM`、全部 `medium`、分类互异。
- 代码提交仅更新目标题；三题评审完成前不能结束算法轮。
- 非算法题和非进行中轮次无法提交算法代码。

前端：

- 模拟面试中心选择多轮后要求简历，启动或恢复并跳转正确会话。
- 面试记录能筛选并继续多轮会话。
- 算法页默认显示第一题，Tab 切换保留每题的语言、草稿、评审与提交状态。
- 文字、语音、知识库面试既有启动和记录入口保持可用。

验收：用户从模拟面试中心选择多轮、绑定简历后，可在算法轮中在三道 Medium 算法题之间切换并独立提交；完成后能推进后续轮次；退出后可从面试记录或最近面试继续该会话。
